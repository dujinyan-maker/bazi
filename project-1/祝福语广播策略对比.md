# 祝福语广播策略对比

## 方案对比

### 方案一：发送时广播（当前实现）

**实现方式**：用户发送祝福语后，立即广播新添加的单条祝福语

**优点**：
- ✅ **实时性好**：新祝福语立即推送给所有客户端
- ✅ **效率高**：只传输一条新消息，网络开销小
- ✅ **响应快**：不需要查询数据库，直接广播
- ✅ **适合弹幕场景**：类似弹幕，逐条显示

**缺点**：
- ❌ **新客户端没有历史数据**：新连接的客户端需要单独调用 REST API 获取历史消息
- ❌ **如果客户端断开重连**：会丢失断开期间的消息

**适用场景**：
- 弹幕系统（类似B站弹幕）
- 实时聊天
- 实时评论

**当前实现代码**：
```java
// 在 sendMessage() 中
BlessingMessageResponse response = buildResponse(message);
webSocketService.broadcastBlessingMessage(response); // 只广播新消息
```

---

### 方案二：查询所有祝福语再广播

**实现方式**：定期查询最新的 N 条祝福语，广播完整列表

**优点**：
- ✅ **数据完整**：所有客户端都收到完整的列表
- ✅ **新客户端友好**：新连接也能收到最新列表
- ✅ **容错性好**：即使客户端断线重连，也能收到最新数据

**缺点**：
- ❌ **效率低**：每次都要查询数据库，网络开销大
- ❌ **实时性差**：需要定期查询，不是即时推送
- ❌ **资源消耗**：频繁查询数据库，增加服务器负载
- ❌ **数据量大**：传输完整列表，网络带宽占用高

**适用场景**：
- 需要完整数据同步的场景
- 定期刷新列表的场景

---

## 推荐方案：混合方案（最佳实践）

### 策略：发送时广播新消息 + 连接时推送完整列表

**实现逻辑**：
1. **新客户端连接时**：推送最新的 N 条祝福语列表（初始化）
2. **发送新祝福语时**：只广播新添加的单条祝福语（增量更新）

**优点**：
- ✅ 结合两种方案的优点
- ✅ 新客户端有完整数据
- ✅ 新消息实时推送
- ✅ 效率较高

**代码实现**：
```java
// 1. 新连接时推送完整列表
afterConnectionEstablished() {
    // 推送最新的 50 条祝福语
    List<BlessingMessageResponse> latestMessages = blessingMessageService.getAllMessages(50);
    broadcastMessage("blessing_list", latestMessages);
}

// 2. 发送时只广播新消息
sendMessage() {
    BlessingMessageResponse response = buildResponse(message);
    broadcastMessage("new_blessing", response);
}
```

## 方案选择建议

### 场景一：纯弹幕系统（推荐方案一）
如果你希望像弹幕一样，只显示新的祝福语，不需要完整历史：
- ✅ 使用**方案一**（发送时广播）
- 客户端连接后自己调用 REST API 获取历史数据

### 场景二：完整列表同步（推荐方案二）
如果你希望所有客户端都保持相同的完整列表：
- ✅ 使用**方案二**（查询后广播）
- 定期（如每5秒）查询并广播

### 场景三：最佳体验（推荐混合方案）
如果你希望兼顾实时性和数据完整性：
- ✅ 使用**混合方案**
- 连接时推送完整列表，新消息时增量推送

## 性能对比

假设有 100 个客户端连接，50 条祝福语：

| 方案 | 单次广播数据量 | 数据库查询 | 网络带宽 | 实时性 |
|------|--------------|-----------|---------|--------|
| 方案一（发送时广播） | ~200字节/条 | 无 | 低 | 立即 |
| 方案二（查询后广播） | ~10KB（50条） | 每次查询 | 高 | 延迟 |
| 混合方案（连接+发送） | 连接时10KB，发送时200B | 连接时查询 | 中等 | 立即 |
